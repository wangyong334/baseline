# BST-SNN 本地验证与尚未成立的主张

日期：2026-11-11。本文记录可以追溯到本地文件的工程验证和小样本探针。没有服务器完整训练结果，没有用完整 test 集选择配置，也没有证据支持“新模型已经优于 V11”或“已经实现在线端到端 GPU 加速”。方法定义见 [BST_METHOD.md](BST_METHOD.md)，运行命令见 [README_SERVER.md](../README_SERVER.md)。

## 1. 当前结果的有效范围

已训练的小模型位于 `Res/bst_local_20261111/train_smoke/`，配置位于 `Res/bst_local_20261111/probe_config.json`。使用 8 条 train 录像；VoW 拟合使用 `val_000`、`val_002`；选择与对照使用 `val_001`、`val_003`。这两条选择录像共 111,144 个事件。训练只跑了 3 个 epoch，背景查询预算为每条录像 2,048，验证代理预算为 512；它不是完整主实验。

这个旧 checkpoint 没有 `band_kind`，因此复现时使用 `sym` 对称出生区间。正式配置现在显式采用 V11 形式的 `martingale` 出生区间，但仅作为启发式规则，不声称当前学习概率已经满足真实后验鞅假设。两种配置应分别记录，不能把旧探针的结果当作正式默认配置的结果。

完整链路测试随后发现在线执行器使用的初始状态字段共享张量：原位回填会让首窗口的当前分数、旧分数和先验互相覆盖。模型已改为独立状态字段，测试已复现故障并验证修复。因此原 `eval_band_fixed/`、`eval_band_learned/`、`eval_learned_learned/` 和旧在线烟测中的性能数字只保留为审计记录，不能直接进入论文表格。三组评估已在修复后重跑，下文仅使用名称带 `_verified` 的新目录。

截至最终检查，新 BST 完整测试套件在 Python 3.8 / PyTorch 1.9.1 和 Python 3.11 / PyTorch 2.11 两个环境中各运行一轮，均为 61 项全部通过。测试张量默认在 CPU，这不是“GPU 单元测试通过”；真实 CUDA 执行由训练和完整在线探针单独覆盖。旧 V11 的 17 项测试、旧 VoW 的 10 项测试也通过，新代码通过 Python 3.8 `compileall`。新套件运行方式为 `python -m unittest discover -s tests -p 'test_bst*.py'`。

## 2. 已确认的代码性质

`tests/test_bst_pipeline.py` 的 3 项完整链路测试已在 Python 3.8 / PyTorch 1.9.1 CPU 下通过。测试使用非零证据模型，覆盖乱序原始事件行、空窗口、多个出生窗口，以及剩余 0/1/2/3 步的尾部截止时间，逐事件、逐合法步骤比较：

- 离线训练 `rollout` 与在线队列的分数及全部 VoW 输入特征一致；空窗口中的分数增量为零，年龄仍推进。
- 跨查询共享来源、单独编码查询、改变批大小，都不改变相应轨迹。
- 提前提交一个查询后，其他查询的分数与状态不变；已提交查询的原始观测仍能被后续查询读取。

专门测试还覆盖旧邻居随新观测重新赋权和重新赋值、未来信息屏蔽、空邻域、阈值和错误代价匹配、冻结策略回报不使用真值挑选动作、有限缓存、先验导出身份与录像尾部空窗口。

本轮同时修复了两个容易使离线与在线不一致的问题：空窗口时 `previous_score` 必须同步到当前分数；录像长度必须保留真实末尾空窗口，不能从最后一个事件推断完整时长。

真实单事件的可解释诊断见 [val_001_event_21507.json](../Res/bst_local_20261111/explanation/val_001_event_21507.json)。它使用较充分拟合的提交头，保存 11 个合法前缀、231 个共享来源的权重、值和实际贡献；逐邻居贡献之和重构总修正的最大绝对误差约为 3.19e-7。该样本的策略等到第 10 步提交，只用于核验可解释量和重审轨迹，不证明所有事件都需要等待。贡献是拟合网络的代数分解，不是真实因果影响或独立似然比。

该轨迹的 [PNG 诊断图](figures/bst/06_real_event_explanation.png) 与 [可编辑 SVG](figures/bst/06_real_event_explanation.svg) 已生成并目视核对，显示信念修正、两种预测代价、旧邻居重新赋值及新旧来源贡献之和。它是五张结构图之外的第六张实测诊断图。

## 3. 小样本训练给出的信息

3 个 epoch 的训练前缀 BCE 分别约为 0.006202、0.005796、0.005524；选择录像的加权前缀 BCE 分别约为 0.011350、0.011558、0.011679。训练目标下降而这项验证指标未改善，说明短训练已经存在泛化或目标匹配问题，不能只展示训练损失下降。该旧探针按前缀 BCE 选取权重；正式配置另外公开了区间策略 IoU 的选择指标，这一改动需要新的验证，不能补写成旧实验已经使用。

VoW 拟合共使用 6,755 个查询样本。该文件统计从 BIR 初始判决到 SDU 截止判决有 1 个纠错样本、10 个误伤样本；这些是抽样查询上的计数，不是总体纠错率，也不是仅由未来窗口造成的增益。等待头难以学习出稳定收益，可能首先源于可利用的后验改善极少，而不只是等待头容量不足。

首次较短拟合的 IoU 增加来自移除 24 个假阳性，同时损失 5 个原先识别正确的目标事件，没有救回原先漏掉的目标事件。Pd 和 ACC 均下降，不能概括为“全面提高精度”。该学习提交头只减少 258 次查询更新，约 1.56%，目标平均观察等待只减少约 0.28 ms，未显示实质等待收益。首次学习出生保持相同精度，却开启更多查询并增加等待，因而没有依据升级为默认路径。

随后在相同冻结 SDU 上增大 VoW 拟合量，见 [policy_extended.json](../Res/bst_local_20261111/train_smoke/policy_extended.json) 和 [扩展拟合评估](../Res/bst_local_20261111/eval_band_extended_final/summary.json)：只使用原有 `val_000/002`，背景预算从 1,024 增至 4,096，拟合轮数从 5 增至 20，策略迭代从 2 增至 3。共 12,899 个拟合查询，仍未使用 test。该探针匹配正式配置的拟合轮数，但训练规模仍小。

较充分拟合后，查询更新数相对固定等待减少约 46.2%，目标额外等待减少约 45.5%，出现了值得继续验证的调度收益。IoU 为 0.861946，来自移除 31 个假阳性并损失 6 个原先正确的目标事件，仍没有救回漏检目标。它说明“第一次短拟合几乎不提前退出”不能被当成 VoW 必然无效的结论，也不能据此宣布已经解决弱目标补救问题。以上仅是同两条选择录像上的适应性开发探针，不能用反复观察同一小验证集来证明泛化；首次失败结果和扩展拟合结果均保留。

这三个旧结果的 `probe: false` 只表示本次评估命令没有再指定 `--limit`，不表示模型经过完整训练或完整验证集评估。其 checkpoint 录像清单本身已缩减，旧先验缺少骨干哈希和完整录像时长元数据；身份与时长仍未完成严格核验。目录名 `_verified` 表示本次状态修复后的重跑，不代表解决了这些旧数据来源限制。正式结果必须使用完整、有来源记录的导出缓存重新训练和评估。

新的扩展拟合评估已按实际数据覆盖范围输出 `probe: true`：train 为 8/99 条，val 为 4/24 条，并保留 `prior_provenance.verified: false`。该元数据修复不改变前面旧实验的范围。

## 4. GPU 微基准与批缓存的局部改善

来源：[当前 GPU 微基准](../Res/bst_local_20261111/kernel_benchmark.json)、[关系缓存前记录](../Res/bst_local_20261111/kernel_benchmark_before_cache.json)、[CPU 冒烟基准](../Res/bst_local_20261111/kernel_benchmark_cpu_smoke.json)。

GPU 为 NVIDIA GeForce RTX 5060 Laptop GPU，Python 3.11.15、PyTorch 2.11.0+cu128，float32，每种设置预热 2 次、计时 5 次。第一轮批大小为 128，下表为墙钟中位数，单位毫秒：

| 合成规模 | 旧 SDU | 新共享模型 | 新共享模型 + 关系缓存 |
|---|---:|---:|---:|
| 10,000 来源 / 500 查询 / 168,000 查询邻居对 | 60.75 | 97.86 | 78.99 |
| 50,000 来源 / 2,500 查询 / 840,000 查询邻居对 | 291.24 | 552.18 | 411.66 |

这一轮新模型在两种规模下都更慢。共享来源编码本身只耗时约 0.39 / 0.99 ms，剩余主要成本在逐查询读取、状态相关重审和重复内核调度，说明“昂贵来源编码被共享”并不自动意味着总体更快。

之后把批大小增至 256，并在不改变方法定义的前提下缓存初始上下文、去掉重复掩码乘法、用批矩阵乘法汇总上下文。来源：[批大小 256 的优化前记录](../Res/bst_local_20261111/kernel_benchmark_batch256.json)、[优化后记录](../Res/bst_local_20261111/kernel_benchmark_optimized_batch256.json)。同轮优化后结果为：

| 合成规模 | 旧 SDU | 新共享模型 | 新模型 + 关系缓存 | 关系缓存 + 前缀裁剪 |
|---|---:|---:|---:|---:|
| 10,000 来源 / 500 查询 | 40.80 | 51.28 | 31.18 | 31.98 |
| 50,000 来源 / 2,500 查询 | 206.68 | 330.05 | 202.23 | 193.72 |

普通共享读取仍慢于旧实现；完整轨迹的关系缓存路径在小规模上约快 1.31 倍，大规模上只约快 1.02 倍，另加前缀裁剪时约为 1.07 倍。这是局部微基准改善，不能外推到真正在线队列。当前训练 `rollout` 使用批内关系缓存，`stream.py` 在线路径仍逐次构建可见关系；后者不能提前编码未来来源。缓存和前缀裁剪的输出最大差异在本合成基准均为 0，但尚未证明同精度下的完整系统加速。

本微基准的新模型参数为 4,906，旧模型为 52,436；较小规模下，旧 SDU 的额外 PyTorch 分配峰值约 65.89 MiB，新模型带关系缓存约 26.88 MiB。它们只是此微基准中超过常驻输入与权重的额外分配，不是训练总显存，也不是部署内存上界。模型宽度不同，精度未匹配；不能把这些参数或内存比较写成同等效果下的效率优势。

CPU 只运行了 1,000 来源 / 16 查询的小型兼容性基准，新旧墙钟分别约 40.61 / 70.75 ms。这个小规模 CPU 结果不能外推为 GPU 加速，更不能抵消上面的 GPU 负结果。

所有这些微基准均排除 BIR 骨干、磁盘加载、邻居搜索、反向训练、VoW 和真正提前退出。它们不表示端到端吞吐；真实队列的查询更新量减少也不等于同比 GPU 加速。

## 5. 环境与真实 BIR 接口验证

本地 GPU 环境最初存在 NumPy 2.4.6 与现有 OpenCV 的二进制接口冲突。原项目官方指标依赖 `cv2`，所以前述三组修复后对照先在兼容的 Python 3.8 / PyTorch 1.9.1 CPU 环境计算。随后仅在项目 `.venv-gpu` 内将 NumPy 降至 1.26.4，解决了该冲突，基础环境未改动；新的完整 GPU 在线推理和官方指标均已成功运行。旧 CPU 评估耗时仍不能作为 GPU 部署耗时。

正式默认配置另做了 CUDA 训练烟测，来源：[current_config_smoke/training.json](../Res/bst_local_20261111/current_config_smoke/training.json)、[清单](../Res/bst_local_20261111/current_config_smoke/manifest.json)。使用 `martingale` 出生区间、显式 160 窗录像长度和批内关系缓存，在 1 条 train / 2 条 val 上运行 1 epoch、3,046 个查询，耗时约 4.69 秒。它确认新默认路径可以训练，不支持任何精度或吞吐结论；该清单也明确标为缩减数据探针，旧先验来源仍未核验。

新导出器对真实 `val_000` 完成了 160 个窗口、45,361 行事件的 BIR 初始分数导出，目录为 `Res/bst_local_20261111/export_prior_smoke/z0_val/`。来源身份见 [prior_provenance.json](../Res/bst_local_20261111/export_prior_smoke/z0_val/prior_provenance.json)：该文件自身完整，但整个 val split 只导出了 1/24 条，因此目录标记为 `complete: false`、`probe: true`。同身份重跑已验证跳过完整文件，而不会无条件覆盖。

当前加载器还核对每个 NPZ 的骨干哈希是否与目录身份文件一致；策略拟合核对骨干身份和 `log_w`。这些检查保护新的有来源缓存，不能倒推补齐旧探针缺失的身份记录。

旧 `online_bir_smoke` 只执行了 `val_000` 的 10 个窗口；`online_bir_provenance_smoke` 只执行 1 个窗口，并明确记录旧 SDU 清单无法验证骨干身份。它们说明真实 BIR 到在线队列的接口可运行，不能给出完整录像精度结论。修复后完整度、来源身份和计时范围均正确的新结果才可用于进一步比较。

环境修复后的 [online_bir_final_gpu/summary.json](../Res/bst_local_20261111/online_bir_final_gpu/summary.json) 已在两条选择录像上执行完整的 BIR → 共享 SDU → VoW。每条录像为 160 个 50 ms 窗口，即 8 秒，共 111,144 个事件；使用上文较充分拟合的 VoW 和旧 `sym` 出生区间：

| 录像 | 事件数 | 完整在线处理耗时 / s | 其中 BIR 子阶段 / s | 出生查询数 |
|---|---:|---:|---:|---:|
| `val_001` | 54,625 | 4.3278 | 2.6835 | 900 |
| `val_003` | 56,519 | 3.8700 | 2.3553 | 650 |

总处理耗时已经包含 BIR 子阶段，不能把两列相加。GPU 在线结果的 IoU 为 0.861946，与预计算先验的扩展拟合评估相同；其余官方指标也一致。但预计算路径的出生数分别为 898 / 649，在线为 900 / 650，说明不能仅凭最终指标相同就宣称来源分数或每个前缀完全相同。旧训练先验的骨干身份没有哈希可查，阈值邻域的浮点变化和来源差异都尚未被严格排除；输出继续保留 `provenance_verified: false` 与 `recording_horizon_verified: false`。

这证明完整 GPU 在线执行路径可运行；因为没有相同环境、相同输入、相同计时范围的 V11 端到端基线，仍不能宣称端到端加速。当前计时是文件已加载后的因果窗口回放，不包含等待实际传感器采集、磁盘加载、指标与写盘，也未测量实时队列的最坏情况延迟。另有 [online_bir_final_cpu/summary.json](../Res/bst_local_20261111/online_bir_final_cpu/summary.json) 的 10 窗 CPU 烟测，只作为兼容性检查。

`evaluate.py` 测量的是已有 BIR 分数上的 SDU/VoW/索引/缓存；`infer.py` 才包含逐窗口事件表征和 BIR 前向。两者都排除磁盘读取、指标计算和写盘。BIR 卷积仍为稠密执行。

## 6. 尚待解决的实质问题

BIR 保留有界量化记忆骨干，支持 Streaming SNN 的研究主线；新的 SDU / VoW 则是连续状态 MLP 和一次性离散提交的混合读出。本轮未实现全脉冲门控或神经形态算子，论文应明确连续读出的范围。

当前共享来源只有 `[初始 logit, 极性]`。它能够读取原始位置和相对时间，但缺少骨干中间特征或独立运动证据；当初始分数错误且邻居分数同样错误时，后验网络可能没有足够信息恢复目标。这是当前方案的重要信息瓶颈。增大 MLP、增加等待头或宣称注意力可解释，均不能凭空补回丢失信息。

下一轮应先固定骨干、出生规则和官方工作点，检验加入少量共享骨干特征是否增加真实纠错，同时分别测量收益和来源缓存开销。只有 SDU 提供可靠且有变化的未来收益，VoW 的等待判断才有可学习的目标。应继续保留重新赋权/重新赋值消融，确认提升来自旧证据被新证据重新解释，而非仅多读了一批事件。

效率上需要测量关系读取、状态更新与内核调度的具体占比，再决定是否采用更紧凑的活跃队列、按相同年龄组织批次或融合计算。当前结构保留逐事件判断，并没有消除随待判查询数与邻域大小增长的成本。完整服务器实验仍需独立验证多种子、密集录像、精度—等待—算力关系及概率校准。
